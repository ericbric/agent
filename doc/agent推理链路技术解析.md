

# Nginx → Ray Serve → vLLM 全流程梳理


## 一、整体架构概览

一条推理请求从客户端发出到最终拿到结果，会流经四个核心组件：

| 层级 | 组件 | 核心职责 |
|------|------|----------|
| 入口层 | Nginx | 接收请求，做第一层负载均衡，把请求分发给某个 Ray 节点 |
| 调度层 | Ray Serve | 决定请求该由哪个模型处理，再从该模型的多个副本中挑一个来干活 |
| 执行层 | vLLM | 真正跑模型推理，用各种优化手段让 GPU 跑得更快更满 |
| 底座层 | Docker | 把以上所有东西打包成镜像，确保部署到任何环境都能一致运行 |


## 二、第一站：Nginx 入口分流

Nginx 不关心请求的具体内容，也不管后面有几个模型、每个模型有几个副本。它只知道集群里有若干 Ray Serve 节点，负责把请求均匀地送过去。

常用的分流方式有三种：

| 策略 | 说明 |
|------|------|
| 轮询/加权轮询 | 按顺序轮流分发，简单公平。可加权重让性能好的机器多接一些 |
| 最少连接数 | 谁当前处理的请求少，就给谁，能动态适应各节点的实时负载 |
| ip_hash | 根据客户端 IP 算哈希值，保证同一客户端的请求总是落到同一节点 |

> 生产环境中，Nginx 通常只做粗粒度的负载均衡，更精细的路由策略交给 Ray Serve 处理。


## 三、第二站：模型路由——该交给哪个模型

到了 Ray Serve 这一层，第一个要解决的问题是：这个请求应该由哪个模型来处理？

### 方式一：规则路由（最常用）

提前配置好规则，把特定场景的请求绑定到特定模型：

- 客服对话 → 模型 A
- 代码生成 → 模型 B
- 文本翻译 → 模型 C

优点：简单直接，没有额外开销
缺点：每次新增场景都需要人工配规则

### 方式二：显式指定

请求里带 `model` 字段，路由器直接按字段值转发。多数情况下这个字段是网关根据租户信息、接口类型自动填入的默认值。

### 方式三：智能路由

当规则覆盖不了的时候，需要系统自己判断该用哪个模型：

| 方案 | 说明 | 优缺点 |
|------|------|--------|
| 模型自评 | 让模型自己输出置信度或难度分 | 消耗一次模型推理算力 |
| 小模型做裁判 | 专门训练轻量级分类模型，只负责判断路由 | 速度快、成本低，是目前主流方案 |

> 实际系统中，三种方式通常叠加使用：大部分请求走规则路由，边界模糊的请求才触发智能路由。


## 四、第三站：副本选择——选哪个副本干活

模型确定之后，接下来要解决的是：这个模型有多个副本（Replica）在运行，具体选哪一个？

### 4.1 默认方案：二选一（Power of Two Choices）

随机挑两个健康的副本，比较它们各自的排队长度（正在处理的请求数 + 等待队列中的请求数），选负载更低的那个。

> 抽样两个再选优，效果已经非常接近遍历所有副本选最优，而开销小得多。

### 4.2 优化方案：前缀感知路由

专为大语言模型场景设计，核心思想：

> 如果两个请求共享相同的前缀（比如同样的长 System Prompt），把它们发到同一个副本，可以复用之前计算好的 KV Cache，避免重复计算。

工作逻辑：

1. 先检查所有副本的负载是否大致均衡（由 `imbalanced_threshold` 控制）
2. 如果负载均衡，再看当前请求的前缀和各个副本已缓存的前缀匹配度
3. 如果匹配度超过阈值（默认 10%），优先发给那个副本
4. 如果都不匹配，发给 KV Cache 占用率最低的副本，是为了“废物利用”——充分利用那些被浪费的显存资源，同时避免把新请求塞进已经快满的副本里，导致它频繁“清理缓存”而变慢。
5. 如果负载已经不均衡，直接退回"二选一"策略

> **核心原则：负载均衡的优先级永远高于缓存命中率。**

### 4.3 高级定制：自定义 Router

如果需要自己实现路由逻辑，核心问题是：各副本的实时状态从哪里获取？

| 方案 | 工作方式 | 优缺点 |
|------|----------|--------|
| 集中式 | 中心节点收集所有副本状态，路由器每次决策前查询 | 数据准、一致性强，但中心节点可能成为瓶颈 |
| 广播式 | 控制器定期把状态广播给所有路由器，查本地缓存做决策 | 速度快、无额外网络往返，但数据有短暂延迟 |

选择依据：

- 副本少、对准确性要求高 → 集中式
- 副本多、追求吞吐量和低延迟 → 广播式

### 4.4 两条隐性规则

1. **只从健康副本里选**：挂了或响应慢的副本会被自动踢出候选池并触发重启
2. **满了就排队**：所有副本都达到 `max_concurrent_queries` 上限时，请求在路由层排队等待


## 五、第四站：vLLM 副本内部

请求最终被送到某个 vLLM 副本（AsyncLLMEngine 实例），执行流程如下：

```text
请求进入
    │
    ▼
① Tokenize：把文本转成 token 序列，放进调度器的等待队列
    │
    ▼
② Continuous Batching：调度器每一步动态组装 batch
   ├── 新来的请求做 prefill（首次计算）
   ├── 进行中的请求做 decode（逐词生成）
   └── 两者混合在同一个 batch 里，不让 GPU 闲着
    │
    ▼
③ PagedAttention：KV Cache 按固定大小的块来管理
   ├── 不要求连续显存，哪里有空位就塞哪里
   └── 支持多个请求共享同一块物理显存（写时复制）
    │
    ▼
④ Prefill 阶段：把完整 prompt 跑一遍前向计算，结果写入 KV Cache
    │
    ▼
⑤ Decode 阶段：逐 token 生成，一次前向同时处理多个请求各一个 token
    │
    ▼
⑥ 每生成一个 token 就检查停止条件（eos / max_tokens / 指定字符串）
   └── 满足则从 batch 中移除，返回结果（流式或一次性）
    │
    ▼
⑦ 如果配置了多卡并行（张量并行 / 流水线并行）
   └── 多个 GPU 通过 NCCL 通信协同计算，对上层完全透明
```

结果生成后沿原路返回：vLLM 副本 → Ray Serve → Nginx → 客户端。

### 5.1 Continuous Batching

传统做法是"一个请求跑完再跑下一个"或"固定 batch 大小"，如果 batch 里有的请求先结束，GPU 就空转了。

Continuous Batching 让调度器每个步骤都重新组合 batch，动态地把新请求塞进来、把完成的请求移出去，最大化 GPU 利用率。
下面这张图展示了多个请求在时间轴上的交错执行情况：

```text
        step1    step2    step3    step4    step5    step6
         │        │        │        │        │        │
请求A    prefill  decode   decode   decode   结束      │
         │        │        │        │        │        │
请求B    排队     prefill  decode   decode   decode   结束
         │        │        │        │        │        │
请求C    prefill  decode   decode   decode   decode   decode
         │        │        │        │        │        │
请求D    排队     排队     排队     prefill  decode   decode
         │        │        │        │        │        │
         ▼        ▼        ▼        ▼        ▼        ▼
```

**关键理解：**

每一列（step）都是 GPU 干的一次活，**不是一个请求一个请求排队干**。

传统做法是：来一个请求，GPU 老老实实把它从头生成到尾，生成完了才轮到下一个——这样如果一个请求要生成很长，后面的请求就得干等着，GPU 利用率很低。

vLLM 不这么干。它维护一个"当前正在干的活"的名单，每一步都重新拼一次桌子。图里你能看到：

- 请求 A、C 从 step1 就开始了，处理完输入（Prefill）后每一步吐一个字（Decode）
- 请求 B 是 step2 才插进来的
- 请求 D 因为 GPU 手头已经排满了，先排队等了三步，直到有空位（A 快结束腾出位置）才补上去开始处理

**关键点**：图里每一列的几个方块，其实是同一次 GPU 前向计算同时算出来的——GPU 并不是切换着伺候每个人，而是把这一批人的活儿打包成一个大矩阵运算，一次算完。这就是 Continuous Batching 名字里"连续"的含义——"这个批次的成员每一步都在变"，而不是"一批固定的人从头做到尾"。

**A、B 悄悄结束，说明什么**：A 在 step4 生成完就结束了（遇到了停止条件），它立刻从这个"批次"里被摘出去，空出来的位置马上被排队的 D 补上——不需要等这一批全部人都做完才能换人，谁先做完谁先让位，这也是它比传统"死等一批做完再换下一批"效率高的核心原因。

### 5.2 PagedAttention

这个名字来自操作系统里的"分页"（Paging）概念。

传统做法要求每个请求的 KV Cache 占据一段**连续**的显存，会导致：

- **碎片化**：显存里分散着许多小块，都不够大，请求被拒绝
- **浪费**：每个请求按最大可能长度预分配，实际用不了那么多

PagedAttention 的解法——**不再要求连续**：

- 把每个请求的 KV Cache 切成固定大小的小块（Block）
- 这些小块可以散落在显存的任何位置
- 用映射表记录哪些块属于哪个请求、顺序如何

> 显存利用率可以从传统方式的 60% 左右提升到 90% 以上。

### 5.3 写时复制（Copy-on-Write）

专门用于处理"多个序列共享相同前缀"的场景。

**场景举例**：束搜索（Beam Search），两个候选的前 1000 个 token 完全相同，第 1001 个 token 开始分叉。

传统做法：两个候选各存一份完整前缀，显存翻倍。

PagedAttention 的做法：

1. 物理上只存一份前缀，两个候选的逻辑块列表都指向同一块物理显存
2. 到了分叉点，才把当前这个块复制一份，两个候选各自继续往下写

效果：

- **省显存**：前 1000 个 token 只存了一份，只需复制 1 个块（50 token）而非 1000 个 token，节省约 95%
- **省时间**：复制显存（微秒级）比重新跑前向计算（毫秒级）快得多

> 前缀越长，优势越明显。10000 个 token 前缀时，节省比例可达 200:1。

假设块大小是 4 个 token，每个块能存 4 个 token 的 KV Cache：

```text
块1：[中][国][的][首]    ← 共享
块2：[都][是][北][京]    ← 共享
块3：[，][  ][  ][  ]    ← 共享（分叉点在这个块内）
块4：[  ][  ][  ][  ]    ← 还没写过
```
分叉点发生在块3的第2个位置（"北京"后面的逗号之后），候选1要写"它"，候选2要写"同"。

PagedAttention 只复制块3，前面的块1、块2不动：
```text
块1：[中][国][的][首]    ← 继续共享
块2：[都][是][北][京]    ← 继续共享

块3（原）：[，][它][拥][有]  ← 候选1 独占
块3（新）：[，][同][时][也]  ← 候选2 独占（从原块复制后修改）

块4：[三][千][年][的]    ← 候选1 独占（新分配）
块4：[是][政][治][中]    ← 候选2 独占（新分配）
    ↑                          ↑
 候选1独占                  候选2独占
```
只有块3被复制了，块1和块2始终共享，块4是后续各自新分配的。


### 5.4 具体示例：请求"北京天气怎么样"的完整执行过程

拿一个具体的例子走一遍，比抽象讲更清楚。

**第一步：Tokenize**

假设问模型："北京天气怎么样"

这句话被切成 token 序列（简化举例，实际分词可能不完全这样切）：

[北京, 天气, 怎么, 样] → 假设对应 token id [101, 205, 88, 460]

**第二步：Prefill（只发生一次）**

模型把这 4 个 token 一次性喂进去做一次前向计算：

| 位置 | token | 这一步做的事 |
|------|-------|--------------|
| 1 | 北京 | 算出它的 K/V，写入 KV cache |
| 2 | 天气 | 算出它的 K/V，写入 KV cache |
| 3 | 怎么 | 算出它的 K/V，写入 KV cache |
| 4 | 样 | 算出它的 K/V，写入 KV cache；同时用这个位置的 logits 采样出第一个要生成的字 |

假设采样结果是"很"（token id 512）。

这一步结束后，显存里的 KV cache 长这样：

> [北京, 天气, 怎么, 样] 这 4 个 token 的 K/V 已经全部存好

而"很"这个字只是被算出来了，**还没有写入 KV cache**——它是这一步的输出，不是这一步的缓存内容。

**第三步：Decode 第 1 步（处理"很"）**

模型现在只需要处理新的这一个 token"很"（不用重新算前面 4 个，因为它们的 K/V 已经在缓存里了）：

- 用"很"去算它自己的 K/V，追加写入 KV cache
- 现在缓存里变成：[北京, 天气, 怎么, 样, 很] 共 5 个 token 的 K/V
- 同时结合前面全部 5 个 token 的 KV cache，算出下一个字——假设是"热"（token id 733）

**第四步：Decode 第 2 步（处理"热"）**

- 用"热"算出它的 K/V，追加写入缓存
- 缓存变成 6 个 token：[北京, 天气, 怎么, 样, 很, 热]
- 结合这 6 个 token 的缓存，算出下一个字——假设是句号"。"（检测到这是停止符）

**第五步：结束**

遇到停止符，生成停止，最终输出："很热。"

**整个过程串起来看：**

| 阶段 | 处理的 token | 这次算完之后 KV cache 里有几个 token | 产出的新字 |
|------|--------------|--------------------------------------|------------|
| Prefill | 北京、天气、怎么、样（4个，一次性） | 4 个 | 很 |
| Decode 第1步 | 很（1个） | 5 个 | 热 |
| Decode 第2步 | 热（1个） | 6 个 | 。（停止） |

**规律**：Prefill 一口气吃掉一整串已知的输入，Decode 每一步只多吃刚生成的那一个新字——但因为前面所有字的 KV cache 都还留着，所以每一步虽然只算一个新字，却能"看到"前面所有内容的信息，这就是为什么生成出来的话是连贯的，而不是每个字互相不认识对方。

### 5.5 什么是 KV

KV 就是 Attention 机制里每个 token 生成的两组向量：**Key（K）** 和 **Value（V）**。

这个概念比较抽象，用生成"热"这个字的场景来解释：模型在生成"热"的时候，其实是在"回头看"前面每个字，看谁跟当前要生成的内容关系最大。

**KV 的具体含义：**

- **K（Key，键）**：相当于每个 token 的"标签"或"索引"。当你生成新字时，系统会拿新字的信息去和之前所有 token 的 K 做匹配，看谁相关度最高。
- **V（Value，值）**：相当于每个 token 的"具体内容"。找到哪些 K 最匹配之后，就把对应的 V 拿出来加权求和，作为生成下一个字的依据。

**为什么缓存 KV 能加速推理：**

生成"热"的时候：

- 如果不缓存：需要把"北京天气怎么样很"这 6 个 token **重新算一遍**，再生成"热"
- 如果缓存了：只需要算"热"这一个新 token 的 K/V，然后直接查前面 5 个 token 的缓存值即可

两者的计算量差距是 6 倍 vs 1 倍。生成越长，缓存带来的加速越明显——1000 个 token 的上下文，每生成一个新字，缓存方案只需要算 1 个 token，不缓存方案要重算 1000 个 token。

**KV cache 在整个流程中的位置：**

```text
Prefill 阶段：一次性把输入 prompt 的每个 token 的 K/V 全部算好并写入 cache
    │
    ▼
Decode 每一步：只算新生成的那一个 token 的 K/V，追加写入 cache
    │
    ▼
生成下一个 token 时：同时使用【历史 KV cache】+ 【当前新 token 的 K/V】来计算
```
### 5.6 前缀感知路由和 PagedAttention 的关系

| 场景 | 谁负责 |
|------|--------|
| 同一请求内部的多个候选（如并行采样 n=3） | PagedAttention 自己完成物理块共享，不需要路由层介入 |
| 不同请求之间的前缀共享（如多个用户用同一个长 System Prompt） | 前缀感知路由负责把请求引导到同一副本；PagedAttention 负责物理块共享 |

> **一句话总结：前缀感知路由负责"把人凑到一桌"，PagedAttention 负责"到了同桌之后共用食材"。**



## 七、餐厅比喻

| 组件 | 类比角色 |
|------|----------|
| Docker | 标准化集装箱，把厨房设备、食材、菜谱统一打包 |
| Nginx | 门口接待员，只看哪个店人少就把客人往哪带 |
| Ray Serve 模型路由 | 点餐后判断"这道菜归川菜组还是粤菜组做" |
| Ray Serve 副本选择 | 从该组里随机问两个厨师"你们谁手头活少"，选更闲的那个 |
| 前缀感知路由 | 优先把菜交给"刚好备好了同样食材"的厨师 |
| vLLM / PagedAttention | 厨师同时处理好几个菜（Continuous Batching）；工作台按小格子划分（分页显存）；两本书共用前言（写时复制） |


## 八、总结

| 组件 | 核心职责 |
|------|----------|
| Nginx | 入口分流，保证流量均匀进入集群 |
| Ray Serve | 模型路由 + 副本选择，保证请求被正确且高效地分配 |
| vLLM | 实际推理，通过 Continuous Batching、PagedAttention 等优化压榨 GPU 性能 |
| Docker | 环境封装，保证整套系统在任何地方都能一致运行 |
